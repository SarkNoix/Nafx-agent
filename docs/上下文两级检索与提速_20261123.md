# 上下文两级检索与提速（2026-11-23）

## 这次改了什么

核心不是“把历史全塞进去”，也不是“全裁掉”，而是：

1. **每段话落盘时生成摘要**（纯规则，不调模型，避免为了省时间又花一次推理）
2. **回顾时先比摘要**，只拿摘要得分高的候选
3. **候选才回读原文**，用原文重新打分
4. **截断线附近宁可多读一段**，防止“摘要说无关、原文其实有关”

对应文件：

| 位置 | 作用 |
| --- | --- |
| `agent/memory.ps1` | `Get-KeyTerms` / `Get-TextSummary` / `Get-SummaryScore` / `Select-MemoryItems` |
| `agent/agent.ps1` | `Add-SessionTurn` 写摘要；`Get-SessionHistory` 两级检索；裁历史时生成“早期对话摘要”；修复 note 行多引号导致的坏 JSON |
| `scripts/nafx-warmup.ps1` | 预热时带上与 agent 一致的 tools 定义；按 create 流程复刻 |
| `launcher.ps1` | `--cache-prompt`、`--cache-reuse 256` |

## 两级检索的具体规则

### 会话

- 会话文件 `logs/session.jsonl` 每行新增 `summary` 字段。
- `Get-SessionHistory -Task $TaskText`：
  1. 取最近 30 条，先只读 `summary` 粗排；
  2. 取粗排前 10，外加分数在“第 10 名分数 - 3”以内的模糊候选；
  3. 对这些候选回读 `content`，用 `Get-SummaryScore -Text` 精排；
  4. 最终只保留分数 ≥5 的条目，并强制保留最后 2 条，防止对话断线；
  5. 分数不够的闲聊不塞进去，避免无关历史挤占第一步 prefill。
- 老记录没有 `summary` 时，加载时现算，不重写文件。

### 经验

- `Add-Lesson` 新增 `summary`。
- `Get-Lessons`：
  1. 摘要粗排（Top 10 + 模糊区间）；
  2. 回读 `task + mistake + fix` 精排；
  3. 分数 ≥5 才带，仍保留原来的 `RejectTools` 冲突过滤。
- 经验不再拼进 `system`，而是放在任务后面的独立 user 消息。
  这样 system + tools 前缀保持稳定，llama 的 prompt cache 不会因为“这次多带了两条经验”整段作废。

### 裁历史

上下文超预算、必须丢掉中间段时，不再直接丢：

- 把被裁掉的 user/assistant 内容压成一条 220 字以内的“早期对话摘要”；
- 塞回 system 末尾，并注明“只是索引，需要细节回读 session.jsonl”；
- 这样目录名、用户偏好、已经试过的方案不会凭空消失。

## 服务端提速

除了上下文，还动了 llama 的缓存路径：

- agent 请求显式带 `cache_prompt: true`（仅本地模式，API 模式不加，避免网关拒收未知字段）。
- `launcher.ps1` 启动参数加：
  - `--cache-prompt`
  - `--cache-reuse 256`
- `nafx-warmup.ps1` 不再只预热 `prompt.md`，还会按 `create` 流程复刻 tools 定义。  
  预热请求和真实请求的 `tools + system` 前缀更接近，第一步能直接命中 KV 缓存。

## 实测

同一台机器、同一模型 `Qwen3-4B-Instruct-2507-Q4_K_M`、`-c 6144 -t 7`：

| 场景 | 改前 | 改后 | 备注 |
| --- | --- | --- | --- |
| `auto-daily-log` | 约 343s / 440s（不同轮次） | **275s** | 仍 100 分 |
| `local-write-simple` | 约 127s | **20s** | 同题；会话过滤掉无关历史后 |
| `local-mkdir` | 约 89s | **26s** | 经验从 system 移出后 |

另外抽查题库前 6 题（写文件/多行/建目录/读/列/追加）全部 100 分；全量 49 题回归没有在本轮跑完，不能据此声称全量分数。

说明：这些不是严格 A/B 基准，受当时的 cache 状态、页面轮询、内存压力影响；但变化方向一致——**无关历史不再参与第一步 prefill**。

## 仍然存在的上限

- 第一次遇到“没预热过的流程”仍然要冷 prefill。4B Q4 在这台 i3-10105F 上约 26-50 tok/s，2000 token 的冷前缀就是 40-75 秒。
- 如果要继续压第一步，下一步应该做“按流程预热多个前缀”或“进一步精简工具表”，而不是继续裁历史。
- 摘要规则会丢细节，所以最终选中的条目仍然回读原文；模糊区间保留 3 分余量，是刻意的“宁多勿漏”。
